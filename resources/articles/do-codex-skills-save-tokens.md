# Do Codex skills save tokens? What six controlled runs showed

The honest result is not “yes” or “no.” It is **task-dependent**.

I ran six controlled GPT-5.6-sol engineering tasks across two task sizes. Every
variant passed its acceptance gates without a human code correction. On a
small, strongly specified backend fix, the run without a repository skill used
the fewest reported tokens. On a medium dependency-free 2048 implementation,
the lean engineering-loop skill used 54.0% fewer reported tokens than the
control.

That reversal is the useful result. A workflow skill has a context cost, and it
has to earn that cost for the task in front of it.

Disclosure: I maintain
[Codex How To](https://github.com/Phelan164/codex-howto), the open-source
repository containing the skill, fixtures, evaluator, and measurements used
here.

## The claim I wanted to test

The repository treats generated code as an intermediate result. Its
`engineering-loop` skill asks Codex to:

1. scope the task;
2. reproduce the problem or establish a baseline;
3. make the smallest coherent change;
4. run focused and repository-required checks;
5. review the resulting diff; and
6. hand off verified evidence and residual risk.

This is sensible engineering advice. But GPT-5.6-sol already knows a great deal
about software work. Loading a lifecycle skill for every task could repeat
behavior the model would perform anyway, spend extra context, or cause
unnecessary checks.

So the question was narrower than “are skills good?”:

> When does this repository skill improve a completed engineering task enough
> to justify its context and execution cost?

## Quality came before token count

The primary gate was acceptance without a human code correction. Token use,
elapsed time, and retries were secondary.

For each task, three variants started from equivalent fresh Git repositories:

- no repository skill;
- `engineering-loop` v0.2.0; and
- the lean `engineering-loop` v0.4.0.

The model, medium reasoning effort, starting commit, Codex CLI surface,
workspace-write sandbox, task contract, tools, and acceptance criteria stayed
fixed within each task set.

The two skill variants invoked their installed repository skill explicitly.
The control did not install or name that skill. Global personal skills remained
visible to every run, so “no repository skill” does **not** mean an
instruction-free model. In fact, the controls selected global skills
automatically. That is a limitation, but it also resembles a realistically
configured Codex environment.

Reported token totals are Codex CLI input tokens plus output tokens. Cached
input is already included in the input count and was not added twice.

## Result 1: the small fix did not need the lifecycle skill

The first task was a bounded Python inventory defect. Codex had to find an
uncovered zero-quantity boundary, preserve a failing regression before the fix,
implement the smallest correction, run the required tests, review the diff, and
report residual input risks.

| Variant | Accepted | Reported tokens | Elapsed | Retries |
|---|---:|---:|---:|---:|
| No repository skill | yes | 390,144 | 114 s | 0 |
| Full skill v0.2.0 | yes | 418,029 | 125 s | 1 |
| Lean skill v0.4.0 | yes | 401,602 | 125 s | 2 |

All three variants:

- found the same defect;
- added the same two-line guard;
- added a four-line regression test;
- passed focused and complete backend suites;
- removed generated bytecode churn;
- reviewed the final two-file, six-line diff; and
- identified the same untested non-integer and boolean input risk.

The control used the fewest tokens and retries. The lean skill used about 2.9%
more reported tokens than the control, although it used about 3.9% fewer than
the older full skill.

For this task, a strong repository contract plus the model’s existing behavior
was enough. The lifecycle skill added no accepted quality difference.

Read the complete
[backend measurement](https://github.com/Phelan164/codex-howto/blob/main/examples/measurements/gpt-5.6-sol-backend-boundary-2026-07-31.md).

## Result 2: the medium build favored the lean skill

The second task implemented a dependency-free browser version of 2048. It
required four product files, deterministic engine behavior, keyboard and touch
controls, score handling, restart behavior, ten supplied tests, syntax checks,
and a post-run evaluator.

| Variant | Accepted | Reported tokens | Elapsed | Retries |
|---|---:|---:|---:|---:|
| No repository skill | yes | 828,446 | 350 s | 1 |
| Full skill v0.2.0 | yes | 553,179 | 257 s | 1 |
| Lean skill v0.4.0 | yes | 380,767 | 247 s | 0 |

Again, every variant passed:

- all ten supplied engine tests;
- JavaScript syntax checks;
- every post-run evaluator check;
- the dependency-free and no-network constraints; and
- the final evidence and diff review requirements.

The lean skill used:

- **54.0% fewer reported tokens** than the no-repository-skill control;
- **31.2% fewer reported tokens** than v0.2.0;
- **29.4% less elapsed time** than the control; and
- no repeated attempt that added no new evidence.

The key behavioral difference was not simply “do fewer checks.” Browser
execution was unavailable in the sandbox. The lean run established that
limitation and stopped. The other variants explored additional launch routes
after the boundary was already known.

Read the complete
[2048 measurement](https://github.com/Phelan164/codex-howto/blob/main/examples/measurements/gpt-5.6-sol-2048-game-2026-07-31.md).

## The boundary is more useful than a winner

These two task sets suggest a hypothesis worth testing:

- **Small, strongly specified fixes:** a lifecycle skill may repeat behavior
  already supplied by the model and repository instructions.
- **Tasks with several implementation and verification surfaces:** concise
  lifecycle guidance may prevent redundant exploration and help the model stop
  when further verification is unavailable.

This does not mean task size alone selects a skill. Risk, ambiguity,
repository quality, available tools, and the cost of a missed check also
matter. A five-line authorization bug can deserve more process than a
hundred-line static demo.

The practical rule is:

> Use the smallest workflow that protects the acceptance criteria, then measure
> whether it earns its context cost for that task class.

## What this experiment does not prove

Six runs are not a population. The result should be treated as a seed
measurement because:

- there were only two tasks;
- all runs could see the same global personal skill catalog;
- run order was fixed rather than randomized;
- the evaluator knew each variant after execution;
- live browser behavior could not be verified in the sandbox;
- the CLI emitted a model-cache schema warning during the runs; and
- cost and context-noise-line measurements were unavailable.

The game fixture also emphasizes deterministic engine behavior more than
visual polish. A real product task may produce a different boundary.

Negative and neutral replications are therefore more valuable than agreement.

## How to reproduce it

Use three fresh copies of the same task repository:

1. no repository skill;
2. the current full or team-default skill; and
3. a lean skill containing only the essential workflow contract.

Hold constant:

- model and reasoning effort;
- starting commit and dependency state;
- task prompt and acceptance criteria;
- available tools and permissions;
- sandbox and Codex surface; and
- evaluator or rubric.

Pre-register quality gates before any run. Record acceptance, evidence
completeness, required checks, retries, human corrections, elapsed time, and
reported tokens. Do not compare efficiency when a variant fails the quality
gate.

Rotate run order across replications and publish every result, including those
where the skill adds overhead or makes no difference.

The repository includes the
[measurement protocol](https://github.com/Phelan164/codex-howto/blob/main/resources/engineering-loop-measurement.md),
[CSV schema](https://github.com/Phelan164/codex-howto/blob/main/examples/measurements/engineering-loop-runs.csv),
[2048 fixture](https://github.com/Phelan164/codex-howto/tree/main/labs/2048-game-benchmark),
and an open
[replication request](https://github.com/Phelan164/codex-howto/issues/23).

## Where I would like this result to be wrong

The next useful evidence is not another seeded demo from the maintainer. It is a
representative external task:

- a frontend change requiring visual verification;
- an infrastructure change with preview and rollback constraints;
- an ambiguous defect requiring repository exploration; or
- a security-sensitive change where a missed review finding dominates token
  cost.

If you run one, report the starting conditions and quality gates—not just a
token total. If your result contradicts this task-size boundary, that improves
the project.

Inspect, reproduce, or fork the complete package at
[Phelan164/codex-howto](https://github.com/Phelan164/codex-howto). Star it only
if the measurements and workflows are useful enough to revisit.
